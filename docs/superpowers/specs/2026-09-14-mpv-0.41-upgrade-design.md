# mpv 0.41 Upgrade Design

## Goal

Upgrade AnimeWitcher's mpv integration from the current 0.36-era runtime/header assumptions to mpv 0.41.0, adopt `gpu-next` as the target renderer, and preserve Anime4K, Apple builds, and media_kit integration while keeping an explicit `gpu` fallback for rollback and compatibility testing.

## Current state

- `media_kit` is pinned to 1.2.6.
- `media_kit_video` is pinned to 2.0.1.
- `media_kit_libs_video` is pinned to 1.0.7.
- The resolved Apple runtime packages currently come from the media_kit libs packages.
- `third_party/mpv/v0.36.0` contains only the four libmpv headers consumed by the Apple build preparation flow; it is not the runtime itself.
- `scripts/prepare_media_kit_ios_headers.sh` explicitly requires `media_kit_video 2.0.1`, mpv `v0.36.0`, the 0.36 archive checksum, and exact header Git blob hashes.
- AnimeWitcher patches the native Apple implementation of `media_kit_video` during CocoaPods installation for Anime4K and mpv render pacing.
- The Apple path therefore depends on both the libmpv ABI and the exact native source layout of `media_kit_video`.

## Target state

- mpv runtime target: **0.41.0** wherever AnimeWitcher controls or can safely replace the runtime.
- libmpv headers used by local integration code must come from the same mpv release as the runtime they compile against.
- `gpu-next` is the target renderer for the upgraded mpv 0.41 integration.
- `gpu` remains an explicit fallback and comparison path so renderer-specific regressions can be isolated and rolled back without reverting the runtime upgrade.
- Existing media_kit public Dart APIs remain the application-facing playback API.
- A media_kit fork is avoided unless the runtime cannot be replaced safely through supported package/runtime boundaries.

## Architecture

The migration is split into four layers so failures can be isolated:

1. **Runtime inventory and compatibility contract**
   - Record the actual mpv runtime source/version per platform.
   - Record the libmpv client API compatibility used by the native integration.
   - Record the renderer policy (`gpu-next` target, `gpu` fallback).
   - Add executable checks that fail when the resolved package/runtime does not match the declared contract.

2. **Apple header/runtime alignment**
   - Replace the 0.36-only header preparation assumptions with versioned metadata for mpv 0.41.0.
   - Vendor the exact 0.41.0 headers required by the build and verify them by immutable hashes.
   - Ensure iOS/macOS compile against headers matching the runtime actually linked by their media_kit libs package or replacement runtime.
   - Update Anime4K and mpv pacing patches only where upstream API/source drift requires it.

3. **Platform runtime upgrades**
   - Upgrade Windows, Android, macOS, and iOS runtimes independently where media_kit packaging permits it.
   - Do not claim a platform is upgraded when only headers changed.
   - If a platform requires a custom runtime package or fork, isolate that mechanism behind one versioned integration point rather than scattering binary/version assumptions across build files.

4. **Playback verification and renderer rollout**
   - Verify normal playback with `gpu-next` explicitly selected.
   - Keep `gpu` available as a fallback and A/B comparison path.
   - Verify HLS, seeking, pause/resume, subtitles, hardware decode, track switching, and Anime4K on the target renderer.
   - Compare `gpu-next` against `gpu` in the same 0.41 runtime before declaring renderer rollout complete.

## Version and build constraints

- mpv target is exactly **0.41.0** for this project.
- Keep `media_kit 1.2.6`, `media_kit_video 2.0.1`, and `media_kit_libs_video 1.0.7` unless a concrete compatibility blocker requires changing one of them.
- Do not update unrelated Flutter dependencies in this work.
- Keep iOS deployment target at 15.0 unless mpv 0.41 runtime packaging proves that a higher floor is technically required.
- Make `gpu-next` the target renderer for mpv 0.41.
- Keep an explicit `gpu` fallback until playback and Anime4K acceptance checks are complete.
- Do not change Anime4K quality presets or Metal/Eco selection logic as part of this migration.
- Header pins must use exact upstream files and immutable verification hashes.
- Runtime provenance must be documented for every supported native platform before the corresponding plan item can be marked complete.

## Apple integration design

The current Apple build uses a repository-owned helper that copies pinned mpv headers into the resolved `media_kit_video` package before CocoaPods evaluates the package Makefile. The upgraded flow keeps the offline/reproducible behavior but removes the assumption that media_kit's embedded Makefile version is the source of truth.

A repository-owned mpv version manifest will define:

- target mpv tag,
- required header names,
- expected immutable hashes,
- expected libmpv client API compatibility,
- renderer policy,
- platform runtime source/provenance.

The preparation script will validate the resolved media_kit package layout separately from mpv version selection. If the package source layout changes, the patch fails with a targeted error instead of silently applying to an unknown file.

Anime4K patches remain fail-closed: every source transformation must match exactly one expected upstream structure or an already-applied marker. Any drift must fail installation and require an intentional patch update.

## Runtime strategy

Preferred order:

1. Use a current media_kit-provided runtime package if it contains mpv 0.41.0 and matches the required ABI.
2. If media_kit's package is older but supports replacing the native runtime cleanly, provide a repository-controlled versioned runtime integration.
3. Only if neither is safe, fork the smallest necessary media_kit native/runtime package. Do not fork the Dart API package unless unavoidable.

Each platform can reach 0.41.0 independently. The project must expose the actual runtime version in CI/build verification so mixed versions cannot be mistaken for a complete upgrade.

## Renderer policy

AnimeWitcher will intentionally adopt mpv 0.41's `gpu-next` renderer as the upgraded default rather than pinning the legacy `gpu` renderer.

The rollout still separates runtime correctness from renderer diagnosis by preserving a `gpu` fallback. Verification compares:

- mpv 0.41 + `gpu-next`
- mpv 0.41 + `gpu`
- each with baseline playback
- each with Anime4K A+A
- each with Anime4K A+S

`gpu-next` remains the target unless a reproducible correctness or performance regression is demonstrated. Any fallback to `gpu` must be explicit and documented rather than silently changing renderer behavior.

## Testing requirements

Every implementation task must use a failing verification first where practical. The minimum verification matrix is:

- dependency/runtime version checks,
- renderer policy checks,
- Apple header integrity checks,
- Anime4K media_kit patch tests,
- mpv pacing patch tests,
- Flutter analyze,
- Flutter unit/widget tests,
- iOS compile/build,
- macOS compile/build when affected,
- Android compile/build when affected,
- Windows compile/build when affected.

Playback acceptance checks must cover:

- local file playback,
- HLS master playlist playback,
- seek forward/backward,
- pause/resume,
- subtitle enable/disable and track changes,
- audio track switching,
- hardware decode path,
- software decode fallback,
- Anime4K disabled,
- Anime4K A+A,
- Anime4K A+S,
- repeated open/close of the player without crashes or leaked native state,
- `gpu-next` as the normal path,
- explicit `gpu` fallback path.

## CI design

Add a small deterministic verification step that reports and validates the declared mpv integration version and renderer policy independently of full platform builds. Platform jobs must additionally validate the runtime they actually package/link when that information is available at build time.

The normal `ci.yml` test/analyze gate remains unchanged except for adding focused mpv integration tests. Preview/release workflows should consume the same version manifest rather than copying version literals.

## Rollback strategy

The migration remains isolated to `feat/mpv-0.41-upgrade`. Each platform/runtime step should be committed separately. If a platform cannot reach 0.41.0 safely, retain its existing runtime, document the blocker in the plan, and do not merge a misleading partial replacement that only updates headers.

Renderer rollback is independent from runtime rollback: a confirmed `gpu-next` regression may temporarily force `gpu` for the affected platform without reverting mpv 0.41 itself.

A runtime rollback must be possible by reverting the platform-specific runtime commit without undoing independent test/inventory improvements.

## Success criteria

The upgrade is complete only when:

- the actual runtime version is known for every supported native platform,
- every platform marked upgraded actually packages or links mpv 0.41.0,
- headers and runtime are ABI-compatible,
- `gpu-next` is the explicit normal renderer path,
- `gpu` remains a tested explicit fallback,
- Anime4K patches pass their source-drift tests,
- required platform builds are green,
- baseline playback behavior remains correct on `gpu-next`,
- no plan item is marked complete based only on a header/version string change.
